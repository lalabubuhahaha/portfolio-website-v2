# Gravity Edition — Stage 2.1 連續性修正

基準 Commit：`cc48aa90c92dfd7fc1c131aa9872f8387fa26a59`。修正前執行相同行為的程式，僅加入唯讀診斷；修正後使用相同 Chromium、尺寸、DPR 與進度取樣流程。

## 真正原因

先前的停留點測試漏掉了持續捲動中的清屏時序。`--hero-frame` 會在 progress 0.30–0.80 改變 canvas 容器 inset，持續觸發 ResizeObserver。Three.js r160 的 `setSize()` 寫入 canvas width/height，即使重設同一尺寸也會清空 drawing buffer。ResizeObserver 發生在 rAF 繪製之後，而舊程式只在 Reduced Motion 下補繪；因此 buffer 被清空後進入瀏覽器合成，直到下一次 render 才恢復。持續捲動又會再清空，造成「消失 → 停止 resize 後重新出現」。

尺寸變化也使 camera aspect 與物理橫向邊界改變，並重新分配愛心 targets，是額外的不連續來源。但主要整片消失並非球體全部移出視錐：過渡點的估算可視球體仍大於 0、opacity 全為 1，renderer/context 與 Mesh 也未重建，進場計數仍為 1。四段起點實測均為 progress 0、1、2、3。

## 最小修正

- Canvas 固定為整個 viewport；移除 `--hero-frame` 對實際容器尺寸的控制。捲動不再變更 camera aspect、物理 frustum 或 renderer 尺寸。
- 以獨立 Three.js presentation Group 的 uniform scale 與 Y 位移保留 Hero 留白；手機僅調整顯示層水平間距，球體仍為圓球。顯示層按原 Hero factor 平滑還原到 identity，Drop / Shape / Release 繼續使用原物理。
- Ball.position、Mesh 與物理半徑不重建、不重設；滑鼠座標轉回顯示層對應的物理座標。
- resize() 對未變動的尺寸／DPR 直接返回。真正 resize 後在 ResizeObserver 內立即 render，避免合成空白 buffer。
- 原 `simulate()` 區塊逐字保持不變：heroF/dropF/shapeF/flyF、阻尼、重力、碰撞、牆壁與 opacity 公式均未改動。沒有重播入口或 canvas fade。

Header、Hero 文字、Section 02–04 排版／文案、Footer、作品資料、lib/content、/work 篩選、依賴均未修改；沒有 Stage 3 工作。

## 測量方法

每個固定停點等待至少 30 次實際 render，再記錄數值及截圖。可視數量是 opacity > 0.01、且套用顯示層後的 bounding sphere 與攝影機視錐相交的估算；包含部分露出及互相遮擋的球體，不是像素級遮擋計算。平均 XYZ 是 Ball.position 的物理座標，並非螢幕位置。此模擬不是完全可逆，平均位置不需在往返時逐值相同。

Progress 表列目標／實測值；瀏覽器捲動有像素捨入，例如手機 0.70 可能略高於門檻，背景按實測值判斷。修前 CSS 尺寸含小數，而 camera aspect 使用 clientHeight 整數，故比值略有差異。Canvas 尺寸是 CSS px；桌面 DPR 0.5 的 drawing buffer 為 720×450（修正後），手機 DPR 1 為 390×844。這是軟體 GPU 測試設定，不是實體裝置效能保證。清屏取樣是在下一次 rAF 入口觀察「前一次繪製後有 canvas 尺寸寫入、尚未補繪」；另有慢捲截圖實際重現空白。
